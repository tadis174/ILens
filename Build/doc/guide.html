Why ILens

An AI agent that needs to look inside a compiled .NET assembly usually shells out to ildasm (an IL dump) or ilspycmd (a full C# decompile) through a generic Bash tool. Both dump an entire file as text. That output stays in the agent's context as input tokens and is sent again on every later turn, so inspecting a single class can cost thousands of tokens, and the cost recurs for the rest of the session.

The target measured below is ICSharpCode.Decompiler.dll 9.1.0.7988, a 2.4 MB assembly with 741 public types. A full decompile of it costs the same however narrow the question is, which is why the baseline column repeats.

Taskilspycmd costILens toolILens cost
List the public types in a namespace1,041,476 tokensfind_types1,101 tokens
See the API surface of one mid-sized class1,041,476 tokenslist_members554 tokens
Find which types expose a given method1,041,476 tokensfind_methods518 tokens

Measured against ICSharpCode.Decompiler.dll 9.1.0.7988 on 2026-10-09; token figures are character counts divided by 4, not a real tokenizer.

ILens turns assembly inspection into bounded, targeted lookups instead of full-file dumps — which is what makes it cheap enough to leave registered as an always-available tool.

Overview and scope

ILens is an MCP server that speaks JSON-RPC over stdio and exposes tools in four categories: discovery (finding types and methods by name or signature), inspection (a type's members, cross-reference analysis, and what a Harmony mod depends on), decompilation (C# source for a type or one of its members), and comparison (what differs between two builds). It is read-only, restricted to the directories named by --allow-root, makes no network calls, and ships as a single self-contained Windows binary.

Scope. ILens is built for inspecting C# assemblies, and its output is C#. The metadata-driven tools — find_types, find_methods, list_members, analyze — read language-agnostic metadata and work on an assembly produced by any .NET language. decompile and analyze's call_sites kind always emit C#. An assembly compiled from F#, VB.NET, or C++/CLI still decompiles, but constructs the source language has and C# does not may render unfaithfully.

Built on ILSpy

ILens would be nothing without ILSpy. The decompiler, the analyzer infrastructure, and the type system that lets ILens talk about a .NET assembly in C# terms at all are not ILens's work — they belong to the ILSpy team. ILens links ICSharpCode.Decompiler for the decompiler proper and ICSharpCode.ILSpyX for the analyzer infrastructure, and is, candidly, a thin MCP shim on top of both.

That upstream work is MIT-licensed, which is the only reason ILens can exist at all. If ILens is useful to you, please consider giving ILSpy a star. They earned it.

To be clear: bug reports and feature requests about ILens belong on the ILens issue tracker, not ILSpy's. The upstream maintainers should not have to inherit downstream problems on top of their own.

Installation

System requirements: Windows 10/11, x64. The binary is self-contained — no separate .NET runtime install is required.

Recommended: winget

winget install Tadis.ILens

A standard winget portable install. It downloads the release ZIP, extracts it under %LOCALAPPDATA%\Microsoft\WinGet\Packages\Tadis.ILens_*\, and registers ilens as a command alias in %LOCALAPPDATA%\Microsoft\WinGet\Links\ — a directory already on your user PATH if you have ever installed another winget portable package. No admin elevation is needed.

For alternative installers see Appendix A; for updating and uninstalling see Appendix B; for installation troubleshooting see Appendix C.

Integrating with Claude Code

Add an entry to .mcp.json in your project root. The command field is the literal string "ilens" — the installer puts the binary on your PATH, so no full path is needed.

{
  "mcpServers": {
    "ilens": {
      "command": "ilens",
      "args": [
        "--allow-root", "C:\\path\\to\\dlls"
      ]
    }
  }
}

A first install needs a full restart, not just a new session. Two independent gates have to clear before a freshly installed ilens actually launches as an MCP server in a Claude app session.

The first is PATH propagation. Windows captures a process's PATH from the registry when that process starts, and later registry changes do not retroactively reach already-running processes. If ilens is a brand-new entry on your user PATH — true for a first-ever winget portable install, which adds %LOCALAPPDATA%\Microsoft\WinGet\Links\, and for any install.ps1 run, which adds %LOCALAPPDATA%\Programs\ILens\ — an already-running Claude app holds a stale environment, and every Claude Code session inside it inherits that stale environment from the parent app. Subsequent winget updates of an already-installed package do not touch PATH and do not trigger this gate.

The second is MCP-server registration. Claude Code reads .mcp.json only at session start, so editing it inside a running session does not register the new server in that session.

Recovering takes both: fully exit and relaunch Claude app, so the new app process gets the current registry PATH, and then start a new Claude Code session in the relaunched app. Existing Claude Code sessions survive a Claude app restart — the relaunched app reattaches to surviving session processes with their original environments intact — so a resumed session picks up neither change. Only a freshly spawned session inside the freshly launched app clears both gates.

The recipe for a first install via the Claude app: close Claude app entirely → install via winget (or install.ps1) → relaunch Claude app → start a new Claude Code session, not a resumed one.

Each --allow-root flag adds a directory tree from which assemblies may be loaded. Without any --allow-root flags the server cannot load anything at all. Pass the flag more than once to configure several roots. ILens also looks at the top of each root for the assemblies an inspected assembly references, so the assemblies a mod builds against can sit in a root of their own and still resolve when the mod is decompiled. A second flag, --max-total-size <MB>, sets the memory budget described under Security model; --version prints the installed version and exits; any other argument stops the server at startup.

For the equivalent claude mcp add CLI command see Appendix D; for Claude Desktop see Appendix E.

Project-level guidance

Registering the server makes the tools available. It does not by itself make Claude prefer them: left to its habits, a model may still run ildasm or ilspycmd in a shell, read the assembly file directly, or search the web for source that does not match your build. ILens closes that gap itself, through the MCP server instructions it sends, so no project needs a block that names ILens's tools. The README divides setup into two steps: Step 1 registers the server, as described under Integrating with Claude Code, and Step 2 reads as follows.

Clients that do not read server instructions

When a client connects, ILens sends it MCP server instructions: what ILens is for, which directories it can read, and which tool answers which question. Claude Code reads them at the start of every session, in the terminal and in the Claude desktop app's Code tab, so with Claude Code, Step 1 is the whole setup.

Claude Desktop's chat does not read server instructions. For it, and for any other client that does not, add this paragraph to the client's instructions and replace <allow-root> with the directory configured above. It names no tool, so it stays correct when a release renames or merges tools:

## Inspecting .NET assemblies

Assemblies under `<allow-root>` are reachable through the `ilens` MCP server.
Prefer its tools over running `ildasm` or `ilspycmd` in a shell, reading
assembly files directly, or searching the web for source.

If your project's CLAUDE.md or a client's instructions hold the block an earlier ILens README asked you to paste, delete it: it names tools that no longer exist. A client that does not read server instructions takes the paragraph above in its place.

Security model

  • --allow-root flags are mandatory: with no roots configured, no assembly can be loaded at all.
  • Every request validates that the assembly path lies inside one of the configured roots — symbolic links and junctions are resolved to their real target first, so a link planted inside a root cannot point the loader outside it.
  • Path-traversal segments (..) are rejected outright.
  • ILens's memory, as Windows charges it to the process, is bounded by a budget (default 200 MB, set with --max-total-size <MB>): when a call ends above it, ILens closes the assemblies used longest ago until it is back under three quarters of it, so the budget can be exceeded only while calls run; an assembly that alone needs more is reopened for each call, and one whose file alone is larger than the budget is refused.
  • All MCP tools are read-only — no writes to assemblies, no shell-out, no network calls.
  • The server speaks stdio only; it does not open a network port.
  • The allow-root bounds which target assemblies can be inspected — it is not the boundary of every file ILens opens. Decompilation also reads the target's references as type-resolution context: inside the roots, assemblies beside the target and at the top of each allow-root; outside them, the installed .NET runtimes and .NET Framework, the global assembly cache, Windows metadata for WinRT references, and the NuGet package folders (NUGET_PACKAGES or %USERPROFILE%\.nuget\packages) that a .deps.json beside the target names. A reference found inside a root passes the same link check as a requested path, so a link there cannot lead outside the roots either.

Tool reference

Eight tools, all read-only. Every tool except list_allowed_roots takes an assembly path that must resolve inside a configured allow-root; compare takes two, assembly_a and assembly_b. The path and budget errors every assembly-loading tool shares are collected under Troubleshooting rather than repeated per tool.

Any parameter typed as an array also accepts a lone value: kinds: "field" means ["field"], and parameter_types: "string" means ["string"]. This holds for every array parameter on every tool.

Conventions every tool shares

Lists. Every tool that answers with a list takes limit (default 100). The answer opens with a header that counts every entry, not just the ones shown — 87 types:, 3 member changes in BaseShift.Gauge:. An empty answer is the header's own form, No types, so it cannot be mistaken for a truncated one. When the limit cuts the list, the last line says by how much: ... (85 more; raise limit to see all). Lists are sorted by the name they print, so a limit cuts predictably and the order stays stable across builds of the inspected assembly; only the calls call_sites lists within one caller keep their order in the code. Every answer is plain text.

Names. ILens prints a type by its fully qualified name, with . between a nested type and the type enclosing it and a generic type definition in C#'s unbound form: System.Func<,>, System.Collections.Generic.Dictionary<,>.Enumerator. It prints a member in reference form, Type.Method(int, string). Every tool takes these forms back, so a name from one answer can be passed to the next tool. type_name also accepts the reflection form (Outer+Inner, System.Func`2) and an argument list (System.Func<int, bool>, whose argument count is the arity). A name written without arity resolves to the non-generic type when one exists and otherwise to the only type of that name; a name several generic types share, such as System.Func, is an error that lists them.

Type patterns. parameter_types and return_type take patterns rather than exact names. A pattern is a type's name, its full name, the end of its full name after any ., or a C# keyword (int, string). It matches the declared type only, not a base or derived one. List matches any List<T>, List<> any one-argument List, and List<int> only that one. A trailing [] matches an array and * a pointer, int also matches int?, a tuple matches as the ValueTuple<...> it prints as, and a ref, out or in prefix matches only a parameter passed by reference. A type copied from ILens's own output always matches what it came from.

Generated code. The tools that list types or members take include_compiler_generated. Left false, they hide what the compiler or a source generator created: closures, lambdas, iterator and async state machines, anonymous types, backing fields, <PrivateImplementationDetails>, and Unity and Burst source-generator output.

Accessibility. The tools that list API — find_types, find_methods, list_members — take accessibility: public, public_protected (the default, which also covers protected internal and private protected), or all. analyze and compare are never filtered by accessibility, because an analysis or a comparison must see everything.

Types from other assemblies. A type the inspected assembly uses but another assembly defines is known to ILens by name. A tool that needs its definition says where it comes from — System.String is not defined in this assembly; it comes from netstandard, Version=2.0.0.0. — so you know which assembly to inspect instead. analyze answers questions about such a type from the inspected assembly's own references to it, and list_members with include_inherited reads the members of base classes from the referenced assemblies it can find.

Strict arguments. An argument name a tool does not declare is rejected with the list of valid names, and so is a parameter that does not apply to the question asked, such as parameter_name with a kind other than call_sites. A silently dropped filter would return an unfiltered answer that reads like a filtered one.

Discovery

find_methods read-only

Find methods across the assembly by name, parameter types or return type, or list one type's methods with type_name. Any combination of filters narrows the search.

Parameters

assembly required string
Path to the .NET assembly to inspect (must be under an allowed root).
name_contains optional string
Case-insensitive substring of the method's name, without namespace or declaring type.
return_type optional string
Return-type pattern, matched by the rules of parameter_types.
parameter_types optional string[]
Parameter-type patterns, in order; the method takes exactly these. See type patterns.
parameter_count optional int
Number of parameters the method takes. If parameter_types is also given, the two must agree.
namespace optional string
Exact namespace of the declaring type, e.g. System.IO; its sub-namespaces are not included.
type_name optional string
Fully qualified declaring type, e.g. System.IO.File. An exact name asserts the type exists, so a name that resolves to no type is an error rather than an empty list.
type_name_contains optional string
Case-insensitive substring of the declaring type's name, without namespace; cannot be combined with type_name. Matching nothing is an ordinary empty result.
accessibility optional public | public_protected | all
Default public_protected, which also covers protected internal and private protected; all adds internal and private.
include_compiler_generated optional bool
Include what the compiler or a source generator created, such as names starting with <. Default false.
limit optional int
Maximum number of results to list. Default 100.

Returns

A count line, then one method per line, sorted: static when it is, then the method in reference form and its return type:

1 method:
ICSharpCode.Decompiler.CSharp.CSharpDecompiler.DecompileTypeAsString(FullTypeName) → string

That is the form decompile and analyze take, and a parameter list copied from it works as parameter_types. Constructors appear as .ctor and operators as op_*. Property and event accessors are left out; decompile and analyze reach one by its IL name, such as get_Count. No match: No methods.

Errors

  • Both type_name and type_name_contains given — they are mutually exclusive.
  • type_name names no type the assembly defines, names a type it only references, or matches several types.
  • namespace names a namespace in which no type of the assembly lies, not even in a sub-namespace: Namespace not found: ...
  • parameter_count contradicts the length of parameter_types.

See also

find_types to find the type first; decompile with member_name to read a match; analyze with call_sites for its callers.

Inspection

analyze read-only

Run cross-reference analysis on a type or one of its members: who uses, reads, writes, instantiates, overrides or implements it, what it uses, and every call to a method with the arguments each call passes. Omit member_name to analyze the type itself.

Parameters

assembly required string
Path to the .NET assembly to inspect (must be under an allowed root).
type_name required string
Fully qualified type name, e.g. System.IO.File. A type the assembly only references is answered from its references to it.
kind required enum
Which analysis to run. Valid values depend on what the symbol is:
  • Type — used_by, instantiated_by, exposed_by, extension_methods, applied_to, implemented_by
  • Method — used_by, call_sites, overridden_by, implemented_by, uses, implements
  • Property — used_by, read_by, assigned_by, uses, overridden_by, implemented_by
  • Field — read_by, assigned_by
  • Event — used_by, overridden_by, implemented_by
member_name optional string
Member name, e.g. ReadAllText; .ctor names a constructor, and get_X, set_X, add_X or remove_X an accessor. Omit to analyze the type itself.
parameter_count optional int
Number of parameters the method takes, to select one overload. If parameter_types is also given, the two must agree. Needs member_name.
parameter_types optional string[]
Parameter-type patterns that select one overload; see type patterns. Needs member_name.
parameter_name optional string
With kind call_sites, show only the argument passed for this parameter; overloads without it are left out.
non_default_only optional bool
With parameter_name, keep only the calls whose argument is not provably the parameter's default. Default false.
include_compiler_generated optional bool
Include results the compiler or a source generator created, such as names starting with <. Default false.
limit optional int
Maximum number of results to list. Default 100.

Returns

A header that counts the results in the kind's own words, then one result per line in reference form, sorted:

1 user of ICSharpCode.Decompiler.CSharp.CSharpDecompiler.DecompileType(FullTypeName) [declared]:
ICSharpCode.Decompiler.CSharp.CSharpDecompiler.DecompileTypeAsString(FullTypeName)

The other kinds count readers of, writers of, symbols instantiating, members exposing, extension methods for, symbols marked with, overrides of, implementations of, symbols used by, interface members implemented by, and calls to. A member's header says where it was found: [declared], [inherited from Base], or [extension method on X]. No result: No users of ..., in the same words. A use inside a lambda, local function, iterator or async method is reported under the member it was written in, and a use inside an accessor under its property or event.

Fields. read_by and assigned_by on a field follow every use of it, including the uses that take its address: calling a method on a struct field, passing the field by ref, or writing one of its members. When the code that receives the address is in the inspected assembly, ILens reads it to decide, and a method of a framework type that never changes its value, such as int or DateTime, only reads it. Otherwise ILens cannot tell whether the field is read or written, so the method is listed under both questions, and its line names what received the address:

FieldAccess.Holder.ParseNumber(string) (may write: passes it by ref to System.Int32.TryParse(string, ref int))

The read_by answer marks the same line (may read: ...).

Properties and events. On a property or event, the usage questions are answered through the accessors, because that is what call sites reference: read_by consults the getter, assigned_by the setter, used_by both, and uses both for the outgoing direction. On an event, used_by covers the add, remove and invoke accessors and, for an ordinary field-like event, the field holding its subscriber list, so the answer includes the code that raises the event and not only the code that subscribes. The header names what was consulted: (via get_Level, set_Level).

Call sites. call_sites lists every call to a method, one per line as the calling member, a colon, and the call, and covers all overloads of the name unless a hint selects one:

8 calls to CallShapes.Mailbox.Send (2 overloads):
CallShapes.Senders.ExplicitDefault(Mailbox): box.Send("explicit")
CallShapes.Senders.InIterator(Mailbox): box.Send("iterator", null, 900)
CallShapes.Senders.InLambda(Mailbox): box.Send("lambda")
CallShapes.Senders.Named(Mailbox): box.Send("named", null, 600)
... (4 more; raise limit to see all)

A call is written as decompiled C# with its arguments in parameter order, so it need not read as the source spelled it: a named or reordered argument stands at its parameter's position, with the defaults the compiler filled in before it, trailing arguments equal to their default are left out, and a call to an extension method is written as a static call with the receiver as its first argument, such as Stamps.Stamp(box, "once") for box.Stamp("once"). With parameter_name, each line shows only the argument that parameter receives, as the compiler bound it, so an omitted argument shows the parameter's default; a value that provably is the default is marked (default). non_default_only keeps the other calls, and its header says how many of all calls they are.

Every call is counted twice, once in the IL and once in the decompiled C#. A caller whose counts differ is reported on a line of its own rather than dropped, so an empty answer is a proof of absence:

Not shown: 1 of 1 call in CallShapes.Senders.AsOperator(Mailbox, Parcel), which the decompiled C# does not show as a call

A caller that fails to decompile is reported the same way, and one whose decompiled C# shows more calls than its IL holds on a Check: line.

Overrides. C# compiles a call to a virtual method as a call to the declaration that introduced it, not to an override. call_sites on an override therefore lists the calls whose receiver's type is the override's class or derives from it, including calls through base., and used_by on an override lists only what refers to the override itself. Both end with a line naming the declaration code calls:

3 calls to CallShapes.Animal.Die(int):
CallShapes.Dog.Die(int): base.Die(cause + 1)
CallShapes.Undertaker.OnAnimal(Animal): animal.Die(2)
CallShapes.Undertaker.OnDog(Dog): dog.Die(3)
Override: code calls CallShapes.Creature.Die(int) instead; listed are those calls whose receiver's type is CallShapes.Animal or derives from it.

When that declaration lies in another assembly, the line says so, and call_sites cannot count the calls made through it. A member that implements an interface member explicitly is never called by name, so the usage kinds end with a line naming the interface member code reaches it through: Explicit implementation: code reaches it only through ExplicitMembers.IShape.Area(); ask about that member for its uses.

Types from other assemblies. For a type the assembly does not define, every type kind and used_by, read_by and assigned_by on a member are answered from the inspected assembly's references. An empty answer about a name nothing in the assembly names adds This assembly neither defines nor references a type of that name., and one about a member it does not reference lists the members it does.

Errors

  • The kind does not apply to the symbol's category: Analysis kind 'read_by' is not valid for Method. Valid kinds for Method: ...
  • applied_to on a type that does not derive from System.Attribute, and implemented_by on a type that is not an interface — an empty result would be indistinguishable from "applied nowhere" or "implemented nowhere". For a type from another assembly, implemented_by errors only when the inspected assembly derives a class from it.
  • read_by on a write-only property, or assigned_by on a read-only one: the accessor the question resolves to does not exist.
  • A property or event that declares no accessors, which only malformed metadata produces.
  • parameter_name or non_default_only with a kind other than call_sites; non_default_only without parameter_name; a parameter_name no overload has (the message lists the parameters); and non_default_only for a parameter without a default value.
  • parameter_count or parameter_types without member_name.
  • On a member of a type from another assembly, uses and implements (the body is in the other assembly), call_sites, overridden_by and implemented_by are refused with the reason, and a type-only kind is refused with a member name.
  • The member does not resolve, or a base class from another assembly declares it — see the member-name errors under Troubleshooting.

See also

decompile to read a result's body; find_methods for name-shaped rather than reference-shaped search.

find_harmony_dependencies read-only

List what a Harmony-patching assembly depends on: every patch target, from [HarmonyPatch] attributes, TargetMethod or TargetMethods bodies and Harmony.Patch calls, and every field it reaches through AccessTools, Traverse or Type.GetField, or takes as a ___name patch parameter. Built to answer "do my patches still bind on the new version?"

Harmony, by Andreas Pardeike, is the library mods use to patch .NET methods at run time. ILens reads its attributes and calls in an assembly without including or running Harmony.

Parameters

assembly required string
Path to the Harmony-patching assembly to scan (must be under an allowed root).
limit optional int
Maximum number of results to list. Default 100.

Returns

A count line, then one dependency per line, sorted by target so that everything depending on one member stands together: the patch kind or Field, the target, <-, the method that depends on it, and in brackets how the target was found:

Prefix HarmonyMod.TargetA.Compute(int) <- HarmonyMod.FieldAccessPatch.Prefix [TypedAttribute]
Postfix HarmonyMod.TargetA.PrivateMethod <- HarmonyMod.StringTargetedPatch.Postfix [StringTargeted]
Field HarmonyMod.TargetI.count <- HarmonyMod.InjectedFieldsPatch.Prefix [Injected]
Prefix HarmonyMod.TargetK.Run <- HarmonyMod.ManualPatches.BeforeRun [PatchCall in HarmonyMod.ManualPatches.Apply]

The patch kinds are Prefix, Postfix, Transpiler, Finalizer and ReversePatch, found as Harmony finds them: by the method's name or by its marker attribute, such as [HarmonyPrefix]. A class counts as a patch class when it carries [HarmonyPatch], has a TargetMethod or TargetMethods, or has a patch method carrying a [HarmonyPatch] of its own. A patch target is found by one of these:

LabelWhere the target comes from

TargetMethodThe one target a TargetMethod returns.
DynamicTargetMethodA TargetMethod with more than one target, typically chosen by a ternary or a switch, or with a target the scan cannot read, so its binding depends on the branch taken at run time.
TargetMethodsEach target a TargetMethods returns or yields.
TargetMethodSearch, TargetMethodsSearchA target the body finds by searching one class's methods for an exact name. The line names no overload, since the search's own tests pick one.
PatchCall in X, PatchCallSearch in XA Harmony.Patch call: a line for each patch method it passes, of the kind its argument's position gives, and each target. X is the member that writes the values out: the calling member, or the caller or construction its values come through. The Search form marks a target found by a search, as above.

It is listed on each class the patch targets; Harmony looks the field up in the class that declares the patched method, which differs when that method is inherited.

Harmony's extension spelling of a lookup, typeof(X).Method("Y"), counts as the lookup it spells. Targets are written as the other tools name them. A target carries its parameter types where the patch pins an overload; without them the line names no overload. A getter or setter patch names the accessor, get_X or set_X; an indexer patch the indexer's accessor, named from the class when the scanned assembly defines it and otherwise by C#'s default, get_Item or set_Item, with ? for a setter's value type it cannot read; an event patch add_X or remove_X; a constructor patch .ctor or .cctor, written .ctor() without argument types because Harmony then binds the parameterless one; a finalizer patch Finalize; and an operator patch the operator's method, such as op_Addition. A method kind the name does not show follows in parentheses, as in HarmonyMod.TargetH.Items (Enumerator).

In TargetMethod and TargetMethods bodies, Harmony.Patch calls and field lookups alike, the scan reads a method from AccessTools' method, property-accessor and constructor lookups, AccessTools.EnumeratorMoveNext and AsyncMoveNext, Type.GetMethod, a property's accessor taken from its PropertyInfo, the method a SymbolExtensions.GetMethodInfo lambda calls, and a search of one class's methods by an exact name, each also when the code makes a generic method of it with MakeGenericMethod. It reads a class from typeof; from text, as in "Namespace.Type:Member", AccessTools.TypeByName, Type.GetType and Assembly.GetType; from AccessTools.Inner or GetNestedType for a nested class; and from GetType() on the calling object, read as the class that declares the calling member. It follows a value back to where the assembly writes it: through locals, through a helper's parameters to each call of the helper, through the fields of a patch object to each place that builds it, through the mod's own methods to what they return, and through a list of names the code writes out and loops over. A Traverse takes the class the decompiler gives the object it was created from; that is a static type, so it names a base class when the field is declared in a subclass.

What the scan cannot read prints ? instead of being left out, so a missing line is a proof of absence. A target it cannot determine is ?. A field is written ?.name or Class.? when one part is unread, and ? when both are; a field name a helper takes from its callers gets a line of its own, ?.name while the class stays unread. A Harmony.Patch call the IL shows but the decompiled code does not prints ? ? <- ? [PatchCall in X], and such a field lookup a Field ? line. Two arguments of one call that each have several values are not paired, and the call reads as ?. A TargetMethod's targets are the values it returns or yields: one it cannot read adds a ? line beside the targets it reads, so an incomplete list says so, while a lookup that only serves a condition counts for nothing. A lookup that takes a FieldInfo prints nothing, since that FieldInfo comes from a lookup listed on its own. Nothing found: No dependencies.

TypedAttribute and StringTargeted tell a target named through typeof and nameof from one named by a string, which breaks silently when the member is renamed. ILens tells them apart by whether the named member is public on the target class, since nameof cannot reach a non-public member, and it can check that only when the target class lives in the scanned assembly. A class named by a string, through HarmonyPatch(string typeName, string methodName, MethodType), is StringTargeted wherever it lives, and a patch Harmony binds by its kind alone, on a constructor, finalizer, operator or indexer, is TypedAttribute wherever it lives, since typeof then names the whole target. Other targets in another assembly, the usual case for a mod, show as Attribute. Only Harmony 2.x, the HarmonyLib namespace, is recognized.

Errors

Only the shared path and budget errors.

See also

compare against two versions of the patched assembly, to see whether each target still exists and what changed in it.

Decompilation

decompile read-only

Decompile a type, or one of its members, to C#. Omit member_name for the whole type.

Parameters

assembly required string
Path to the .NET assembly to inspect (must be under an allowed root).
type_name required string
Fully qualified type name, e.g. System.IO.File.
member_name optional string
Member name, e.g. ReadAllText; .ctor names a constructor, and get_X, set_X, add_X or remove_X an accessor.
parameter_count optional int
Number of parameters the method takes, to select one overload. If parameter_types is also given, the two must agree.
parameter_types optional string[]
Parameter-type patterns that select one overload, e.g. ["int", "bool"]; see type patterns.

Returns

Without member_name, the whole type as C# — the most expensive read in the tool set. With it, a comment naming what resolution picked, then the code:

// ICSharpCode.Decompiler.CSharp.CSharpDecompiler.DecompileTypeAsString(FullTypeName) → string
using ICSharpCode.Decompiler.TypeSystem;

public string DecompileTypeAsString(FullTypeName fullTypeName)
{
	return SyntaxTreeToString(DecompileType(fullTypeName));
}

The comment carries a method's parameter and return types, so a mismatch against what was asked for is visible, and names the origin when the member is not declared on the type asked about: [inherited from Base] or [extension method on X]. A method or an accessor gives its body. A property or event name gives the whole declaration with its accessor bodies, and a field name the field's declaration with the initializer the compiler moved into the constructors. A member that implements an interface member explicitly is reached by the interface member's plain name when no ordinary member has that name. A member that a base class from another assembly declares is not decompiled here: the error names the file that holds it.

Errors

  • parameter_count or parameter_types without member_name.
  • No member of that name on the type, its base types, or as an extension method.
  • Several overloads match and the hint cannot narrow them, or no overload satisfies the hint; the message lists the candidates found across the inheritance chain.
  • The name exists as more than one kind of member, as several indexers (name one by its accessor, get_Item or set_Item, with parameter_types), or as several explicit interface implementations (pass the full name of one).
  • An accessor name for a property or event without that accessor: Property 'Count' on ... has no setter.
  • The member is declared on a base class another assembly defines; see Troubleshooting.
  • parameter_count contradicts the length of parameter_types.

See also

list_members first, to see what a type has without paying for bodies; analyze for who uses what you are reading.

Comparison

compare read-only

Compare two versions of an assembly, from the types that differ down to one method: without type_name the changed types, with type_name that type's member changes, and with member_name the method's or accessor's two bodies, or only a verdict when they print alike.

Parameters

assembly_a required string
Path to the first assembly (must be under an allowed root).
assembly_b required string
Path to the second assembly (must be under an allowed root).
type_name optional string
Fully qualified type name, to list that type's member changes.
member_name optional string
A method or accessor of that type, to show its two bodies. Needs type_name.
parameter_count optional int
Number of parameters, to select one overload. Needs member_name.
parameter_types optional string[]
Parameter-type patterns that select one overload. Needs member_name.
namespace optional string
Exact namespace to restrict the changed-types list to; applies only without type_name.
include_compiler_generated optional bool
List the generated types and members under their own names as well, compared as they stand; applies only without member_name. Default false.
format optional csharp | il
How to print the two bodies: csharp (the default) decompiles them, il disassembles them as the comparison reads them. Applies only with member_name.
limit optional int
Maximum number of changes to list. Default 100.

Returns

Every line starts with + for what only B has, - for what only A has, and ~ for what both have but changed. Without type_name:

7 changed types:
~ BaseShift.BaseArgumentMover [metadata,bodies]
~ BaseShift.BaseArityMover [metadata,bodies]
~ BaseShift.Gauge [bodies]
~ BaseShift.Generated.ChangedInside [bodies]
~ BaseShift.Generated.Renumbered [members]
~ BaseShift.InterfaceArgumentMover [metadata]
~ BaseShift.InterfaceArityMover [metadata]

A changed type names what changed: metadata (its base type, interfaces, modifiers, accessibility or kind), members (a member added or removed), and bodies (a method or accessor body changed). With type_name, one line per changed member, as its declaration; a changed property or event names the accessors whose bodies changed, which are what member_name takes next:

3 member changes in BaseShift.Gauge:
~ public event EventHandler Changed [add_Changed]
~ public int Level { get; set; } [get_Level]
~ public int Limit { get; set; } [set_Limit]

A type only one assembly has lists all its members, and the header says , which only A has or , which only B has. With member_name, the two bodies under // === A: path === and // === B: path ===. Bodies that print alike, in either format, get the verdict line alone and no code, since a copy would show nothing that changed; decompile returns the code:

// BaseShift.Generated.Renumbered.LocalFunctionCapturing(int) → int — bodies are identical in both assemblies.

When the C# reads alike while the IL differs, the line ends — bodies decompile alike in both assemblies, but their IL differs; format il shows where. A method only one assembly has is the whole difference, so its code comes alone, under a header saying which build has it:

// BaseShift.Generated.Renumbered.Inserted(int) → long — only B has it.

No change: No changed types, No member changes in ....

Members are matched by name, generic arity, parameter types and passing keywords, and return type, so a changed signature shows as one removal and one addition. A member's accessibility, modifiers and attributes are not compared. Bodies are compared as IL with tokens resolved to names and file positions left out, so a method a rebuild leaves unchanged does not show as changed. The code the compiler generates for a method, such as its lambdas, local functions, iterator and async state machines, and the copy of its code Burst compiles, is compared as part of that method, with the numbers the compiler gives generated names by position set aside: a method added before others does not make them show as changed, and a change inside a lambda shows on the method that contains it. For a method Burst compiles, the C# shown is Burst's copy of its code, and the header names it: (via X$BurstManaged).

Errors

  • A parameter used at a level it does not apply to: member_name without type_name, an overload hint without member_name, namespace with type_name, include_compiler_generated with member_name, and format without member_name.
  • namespace names a namespace neither assembly has: Namespace not found in either assembly: ...
  • The type is in neither assembly: Type '...' not found in either assembly., or, when one of them references it, Type '...' is not defined in either assembly; it comes from ...
  • member_name names a property, event or field, which has no body of its own; the message names the accessors to compare instead, or for a field the constructors that hold its initializer.
  • Neither assembly has a method of that name, or overload resolution fails, by the same rules as decompile.

See also

find_harmony_dependencies for the members a mod depends on; decompile to read a changed type in full.

Troubleshooting

Every tool error reaches the caller as Error: <ExceptionType>: <message>. The messages below are shared by several tools; the ones particular to a tool are listed under that tool.

No allowed roots configured. The server cannot load any assemblies.

The server was launched without --allow-root. Add one or more --allow-root <directory> arguments to the args array in .mcp.json and start a new session. list_allowed_roots reports the same condition without failing.

Path is not under any allowed root: ...

The requested assembly lives outside every configured root. The message lists the roots that are configured. Either point the call at a file inside one, or add the containing directory as another --allow-root.

Path resolves (via a symbolic link or junction) to a location outside any allowed root: ...

The path passed the lexical containment check but resolves to a real target outside the roots. This is the reparse-point check doing its job — a link planted inside a root cannot be used to reach outside it. A chain of links that does not end, or cannot be followed, is rejected with Path has too many levels of symbolic links or junctions or Path could not be resolved through its symbolic links or junctions.

Path contains '..' which is not allowed: ...

Parent-directory segments are rejected before normalization. Pass an absolute path with no .. components.

Assembly file does not exist: ... or Assembly path is empty.

The path is inside a root but names no file, or no path was given. Check the spelling and that the build actually produced the assembly.

Assembly is N MB, which exceeds the M MB total memory budget on its own: ...

ILens holds an assembly's whole image in memory while it is open, so a file larger than the whole memory budget is refused before it is loaded. Raise the budget with --max-total-size <MB>.

Unknown argument '...' for tool '...'. Valid arguments: ...

An argument name the tool does not declare, often a parameter name from an older ILens release. Most filters are optional, so a silently dropped filter would return an unfiltered result that looks like an answer — the call is rejected instead. The message lists the valid names.

The JSON value could not be converted to ILens.AnalysisKind. ...

A value outside the parameter's set of values: here a kind that analyze does not have, and likewise ILens.MemberKind for kinds, ILens.AccessibilityFilter for accessibility, and ILens.CompareFormat for format. The tool's schema lists the valid values, and the tool reference above lists them by parameter.

Type not found: ...

No type the assembly defines or references has that name. When types of that name exist in another arity, the message lists them. find_types with name_contains finds the exact name.

... is not defined in this assembly; it comes from ...

The assembly uses the type but another assembly defines it. Point the call at that assembly to read the type itself; analyze can still answer who in this assembly uses it.

Type name '...' matches N types: ... Name one as listed.

A name written without arity matches several generic types, such as System.Func. Pass one of the listed names, which carry their arity.

Namespace not found: ...

No type of the assembly lies in that namespace or below it. Namespaces are matched exactly and case-sensitively.

Member '...' not found on ..., its base types, or as an extension method.

The name does not exist anywhere on the inheritance chain. list_members lists what the type actually has; an accessor is named with its prefix, get_Count, and a constructor .ctor. When the search stopped at a base class whose assembly ILens could not load, the message says the base types ILens could load and ends with ... and its base types were not searched, since ILens could not load .... Put that assembly beside the inspected one or at the top of an allow-root, and the search goes on into it.

... inherits ... from a base class this assembly does not define; ... comes from ...

The member is declared on a base class another assembly defines, so the inspected assembly holds no code for it. The message names the file that does: call decompile, analyze or compare on that file to read the member.

'...' on ... has N matching overloads; specify parameter_count or parameter_types to disambiguate: ...

The name is overloaded. Pass parameter_types (or parameter_count when the arities differ) taken from the listed candidates.

No overload of '...' on ... matches ...

A parameter_count or parameter_types hint was given and nothing satisfies it. The message lists every same-named overload found across the inheritance chain, so the right hint is usually visible in the error itself — and a confirmed "no such overload" is often the answer that was being sought.

Member '...' on ... is ambiguous — it exists as more than one member kind ...

The name is used by more than one kind of member on the type, which happens only in obfuscated or non-C# metadata. Pass an overload hint if the method is meant. An ordinary C# event does not trigger this: its compiler-generated backing field is recognized as part of the event.

Analysis kind '...' is not valid for ...

The kind does not apply to what analyze resolved the symbol to. The message lists the kinds that do apply to that category.

parameter_count (N) contradicts parameter_types.Length (M).

Both overload hints were given and disagree on the number of parameters. Pass one of them, or make them agree.

Decompiled code shows numbers where names belong, or Unknown result type comments

A referenced assembly is not in an allowed folder. ILens finds an assembly's references beside it, at the top of each allow-root, and in the installed .NET; a reference it cannot find leaves the decompiler without its types, so enum values come out as numbers and expressions of those types are marked as unknown. Add the folder that holds the missing assemblies, such as a game's own assemblies for a mod, as another --allow-root.

The tools do not appear at all

Almost always the two gates described under Integrating with Claude Code: an already-running Claude app holding a stale PATH, or a session that started before .mcp.json existed. Close Claude app entirely, relaunch it, and start a new session. The server also refuses to start when its own arguments are wrong — an --allow-root directory that does not exist, an unknown flag, or a non-numeric --max-total-size. It then writes the reason to stderr as a line starting with [ILens] and exits, which the MCP client typically reports as a server that failed to connect.

Appendix A: Alternative installers

For machines where winget is unavailable or locked down by policy, or when you would rather inspect the binary before granting it execution.

PowerShell one-liner

irm https://raw.githubusercontent.com/tadis174/ILens/main/install.ps1 | iex

Installs to %LOCALAPPDATA%\Programs\ILens\ and adds that directory to your user PATH. No admin elevation is needed.

Manual ZIP

Download ILens-windows-x64.zip from the Releases page and extract it anywhere. Then either add the directory to PATH yourself, or give the binary's full path in .mcp.json's command field.

Appendix B: Updating and uninstalling

winget. winget upgrade Tadis.ILens to update; winget uninstall Tadis.ILens to remove.

PowerShell one-liner. Re-run irm https://raw.githubusercontent.com/tadis174/ILens/main/install.ps1 | iex to update — the script overwrites the install directory in place and stops any running ILens processes first. Uninstall with irm https://raw.githubusercontent.com/tadis174/ILens/main/uninstall.ps1 | iex.

Manual ZIP. No automatic update mechanism — re-download ILens-windows-x64.zip and re-extract on each new release. To uninstall, delete the extracted folder and remove the PATH entry if you added one.

Appendix C: Installation troubleshooting

Antivirus or Windows Defender quarantines ILens.exe

Self-contained .NET binaries are sometimes false-positive-flagged on first sight. Check the quarantine and restore the file, or add an exception for the install directory — %LOCALAPPDATA%\Microsoft\WinGet\Packages\Tadis.ILens_*\ for winget, %LOCALAPPDATA%\Programs\ILens\ for the PowerShell script — before re-running the installer.

SmartScreen shows "Windows protected your PC"

This affects browser-downloaded ZIP installs, which carry Mark-of-the-Web. The winget and PowerShell paths do not. For a manual browser download, click "More info → Run anyway".

winget upgrade Tadis.ILens fails with remove: Access is denied: "...\ILens.exe"

A running ILens MCP server — a Claude Code session, Claude Desktop, or another AI client that registered ILens — holds an exclusive lock on the binary winget is trying to replace. Close every AI client with ILens registered and re-run the upgrade. The PowerShell install.ps1 path handles this automatically by stopping running ILens processes before extraction, so the same upgrade via irm ... | iex needs no manual cleanup. winget's portable installer type has no pre-install hook where an equivalent step could run.

Appendix D: claude mcp add CLI

A programmatic alternative for anyone who would rather not edit .mcp.json by hand:

claude mcp add ilens ilens -- --allow-root "C:\path\to\dlls"

The doubled ilens is intentional: the first is the MCP server alias — the same string that becomes the JSON key in .mcp.json — and the second is the binary on PATH after install. The -- separator before --allow-root is required so claude mcp add does not consume it as one of its own options.
