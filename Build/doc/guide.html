Why ILens

An AI agent that needs to look inside a compiled .NET assembly usually shells out to ildasm (an IL dump) or ilspycmd (a full C# decompile) through a generic Bash tool. Both dump an entire file as text. That output stays in the agent's context as input tokens and is sent again on every later turn, so inspecting a single class can cost thousands of tokens, and the cost recurs for the rest of the session.

The target measured below is ICSharpCode.Decompiler.dll 9.1.0.7988, a 2.4 MB assembly with 741 public types. A full decompile of it costs the same however narrow the question is, which is why the baseline column repeats.

ILens turns assembly inspection into bounded, targeted lookups instead of full-file dumps — which is what makes it cheap enough to leave registered as an always-available tool.

Overview and scope

ILens is an MCP server that speaks JSON-RPC over stdio and exposes tools in four categories: discovery (finding types and methods by name or signature), inspection (a type's members, cross-reference analysis, and what a Harmony mod depends on), decompilation (C# source for a type or member, and a pattern search through it), and comparison (what differs between two builds). It is read-only, inspects only assemblies under the directories named by --allow-root, makes no network calls, and ships as a single self-contained Windows binary.

Scope. ILens is built for inspecting C# assemblies, and its output is C#. The metadata-driven tools — find_types, find_methods, list_members, analyze — read language-agnostic metadata and work on an assembly produced by any .NET language. decompile and analyze's call_sites kind always emit C#, and search_code searches that C#. An assembly compiled from F#, VB.NET, or C++/CLI still decompiles, but constructs the source language has and C# does not may render unfaithfully.

Built on ILSpy

ILens would be nothing without ILSpy. The decompiler, the analyzer infrastructure, and the type system that lets ILens talk about a .NET assembly in C# terms at all are not ILens's work — they belong to the ILSpy team. ILens links ICSharpCode.Decompiler for the decompiler proper and ICSharpCode.ILSpyX for the analyzer infrastructure, and is, candidly, a thin MCP shim on top of both.

That upstream work is MIT-licensed, which is the only reason ILens can exist at all. If ILens is useful to you, please consider giving ILSpy a star. They earned it.

To be clear: bug reports and feature requests about ILens belong on the ILens issue tracker, not ILSpy's. The upstream maintainers should not have to inherit downstream problems on top of their own.

Installation

System requirements: Windows 10/11, x64. The binary is self-contained — no separate .NET runtime install is required.

Recommended: winget

winget install Tadis.ILens

A standard winget portable install. It downloads the release ZIP, extracts it under %LOCALAPPDATA%\Microsoft\WinGet\Packages\Tadis.ILens_*\, and registers ilens as a command alias in %LOCALAPPDATA%\Microsoft\WinGet\Links\ — a directory already on your user PATH if you have ever installed another winget portable package. No admin elevation is needed.

Integrating with Claude Code

Add an entry to .mcp.json in your project root. The command field is the literal string "ilens" — the installer puts the binary on your PATH, so no full path is needed.

{
  "mcpServers": {
    "ilens": {
      "command": "ilens",
      "args": [
        "--allow-root", "C:\\path\\to\\dlls"
      ]
    }
  }
}

A first install needs a full restart, not just a new session. Two independent gates have to clear before a freshly installed ilens actually launches as an MCP server in a Claude app session.

The first is PATH propagation. Windows captures a process's PATH from the registry when that process starts, and later registry changes do not retroactively reach already-running processes. If ilens is a brand-new entry on your user PATH — true for a first-ever winget portable install, which adds %LOCALAPPDATA%\Microsoft\WinGet\Links\, and for any install.ps1 run, which adds %LOCALAPPDATA%\Programs\ILens\ — an already-running Claude app holds a stale environment, and every Claude Code session inside it inherits that stale environment from the parent app. Subsequent winget updates of an already-installed package do not touch PATH and do not trigger this gate.

The second is MCP-server registration. Claude Code reads .mcp.json only at session start, so editing it inside a running session does not register the new server in that session.

Recovering takes both: fully exit and relaunch Claude app, so the new app process gets the current registry PATH, and then start a new Claude Code session in the relaunched app. Existing Claude Code sessions survive a Claude app restart — the relaunched app reattaches to surviving session processes with their original environments intact — so a resumed session picks up neither change. Only a freshly spawned session inside the freshly launched app clears both gates.

The recipe for a first install via the Claude app: close Claude app entirely → install via winget (or install.ps1) → relaunch Claude app → start a new Claude Code session, not a resumed one.

Each --allow-root flag adds a directory tree from which assemblies may be loaded. Without any --allow-root flags the server cannot load anything at all. Pass the flag more than once to configure several roots. ILens also looks at the top of each root for the assemblies an inspected assembly references, so the assemblies a mod builds against can sit in a root of their own and still resolve when the mod is decompiled.

Three more options exist. --max-total-size <MB> sets the memory budget described under Security model. --max-search-seconds <n> sets how long one search_code call may decompile before it answers with how far it came, 45 seconds unless given. A client built on the MCP SDK's defaults gives up on a request after 60 seconds, and the 45 seconds leave a call the time to finish its answer within that, with room for a slower machine; with 0, each call finishes at least one type. --version prints the installed version and exits. Any other argument stops the server at startup.

For the equivalent claude mcp add CLI command see Appendix D; for Claude Desktop see Appendix E.

Project-level guidance

Registering the server makes the tools available. It does not by itself make Claude prefer them: left to its habits, a model may still run ildasm or ilspycmd in a shell, read the assembly file directly, or search the web for source that does not match your build. ILens closes that gap itself, through the MCP server instructions it sends, so no project needs a block that names ILens's tools. The README divides setup into two steps: Step 1 registers the server, as described under Integrating with Claude Code, and Step 2 reads as follows.

Clients that do not read server instructions

When a client connects, ILens sends it MCP server instructions: what ILens is for, which directories it can read, and which tool answers which question. Claude Code reads them at the start of every session, in the terminal and in the Claude desktop app's Code tab, so with Claude Code, Step 1 is the whole setup.

Claude Desktop's chat does not read server instructions. For it, and for any other client that does not, add this paragraph to the client's instructions and replace <allow-root> with the directory configured above. It names no tool, so it stays correct when a release renames or merges tools:

## Inspecting .NET assemblies

Assemblies under `<allow-root>` are reachable through the `ilens` MCP server.
Prefer its tools over running `ildasm` or `ilspycmd` in a shell, reading
assembly files directly, or searching the web for source.

If your project's CLAUDE.md or a client's instructions hold the block an earlier ILens README asked you to paste, delete it: it names tools that no longer exist. A client that does not read server instructions takes the paragraph above in its place.

Security model

  • --allow-root flags are mandatory: with no roots configured, no assembly can be loaded at all.
  • Every request validates that the assembly path lies inside one of the configured roots, both as written and with its symbolic links and junctions resolved to their real target, so a link planted inside a root cannot point the loader outside it.
  • A path outside every root is refused as written, before anything on disk is read, even where a link there would lead into a root.
  • A root may itself be given through a symbolic link or junction: the assemblies under it are then admitted through the link or by their real path, the link is resolved once at startup, so one moved while the server runs is refused until a restart, and a root whose links cannot be resolved, such as one below a folder the server may not list, stops the server at startup.
  • Path-traversal segments (..) are rejected outright.
  • ILens's memory, as Windows charges it to the process, is bounded by a budget (default 200 MB, set with --max-total-size <MB>): when a call ends above it, ILens closes the assemblies used longest ago until it is back under three quarters of it, so the budget can be exceeded only while calls run; an assembly that alone needs more is reopened for each call, one whose file alone is larger than the budget is refused, and the decompiled text search_code keeps for later searches takes at most a quarter of the budget.
  • All MCP tools are read-only — no writes to assemblies, no shell-out, no network calls.
  • The server speaks stdio only; it does not open a network port.
  • The allow-root bounds which target assemblies can be inspected — it is not the boundary of every file ILens opens: decompilation, and every question that reads a type another assembly defines, also reads the target's references as type-resolution context, inside the roots from the target's own directory and the top of each allow-root (a reference there passes the same link check as a requested path), and outside them from the installed .NET runtimes and .NET Framework, the global assembly cache, Windows metadata for WinRT references, and the NuGet package folders (NUGET_PACKAGES or %USERPROFILE%\.nuget\packages) that a .deps.json beside the target names.

Tool reference

Nine tools, all read-only. Every tool except list_allowed_roots takes an assembly path that must resolve inside a configured allow-root; compare takes two, assembly_a and assembly_b. The path and budget errors every assembly-loading tool shares are collected under Troubleshooting rather than repeated per tool.

A value with exactly one reading is taken as the form the schema has, on every parameter of every tool: a lone value for a parameter typed as an array (kinds: "field" means ["field"], parameter_types: "string" means ["string"]); a listed name in another case, without its underscores or with spaces around it (UsedBy means used_by); a whole number given as text, with a zero fraction or with an exponent; "true" or "false" given as text; and null for an optional parameter, which counts as the parameter left out. parameter_types also takes several types in one text, split by the tools themselves: "string, int" means ["string", "int"], and a comma inside angle or square brackets stays in its pattern, as in "Dictionary<int, string>". Any other value a parameter does not take is an error, see Strict arguments.

Conventions every tool shares

Lists. Every tool that answers with a list takes limit (default 100); only decompile and list_allowed_roots take none. The answer opens with a header that counts every entry, not just the ones shown, and an empty answer is the header's own form, No types or No users of ..., so it cannot be mistaken for a truncated one. When the limit cuts the list, a line after it says by how much. A limit of 0 lists nothing, so the answer is the header, which holds the count, and that line; a negative limit counts as 0. Lists are sorted by the name they print, so a limit cuts predictably and the order stays stable across builds of the inspected assembly. Every answer is plain text. find_types on ICSharpCode.Decompiler.dll with namespace ICSharpCode.Decompiler.Metadata and limit 3:

41 types:
ICSharpCode.Decompiler.Metadata.AssemblyNameReference
ICSharpCode.Decompiler.Metadata.AssemblyReference
ICSharpCode.Decompiler.Metadata.AssemblyReferenceClassifier
... (38 more; raise limit to see all)
Not shown: 9 internal or private

The last line is the one find_types, find_methods and list_members end with when their accessibility filter left matches out, so that a list without a private member does not read as "the type has none"; with accessibility public it counts them as non-public. Under an empty answer the line also counts the compiler-generated matches and names the settings that list everything counted, as for the namespace CallShapes.Concealed of the test assembly CallShapes.dll:

No types
Not shown: 1 internal or private, 1 compiler-generated; include_compiler_generated with accessibility all lists them

analyze, which has no accessibility filter, puts such a line under the header of an answer that is empty only because compiler-generated results were left out, before any line of its own, and adds none under a list: No members exposing CallShapes.Callers, then Not shown: 2 compiler-generated; include_compiler_generated lists them. A list whose entries belong to members, the calls analyze lists for call_sites and the lines search_code matches, names each member once, on a line of its own, with its entries beneath it, indented by two spaces and in the order they stand in the code. The header and limit count the entries, not the lines, so a limit can cut inside a member's entries.

Names. ILens prints a type by its fully qualified name, with . between a nested type and the type enclosing it, a generic type definition in C#'s unbound form, System.Func<,> or System.Collections.Generic.Dictionary<,>.Enumerator, and a constructed type with its type arguments, System.Collections.Generic.List<int>. It prints a member in reference form, Type.Method(int, string), with a constructor as .ctor, a generic method with its type parameters after its name, CallShapes.Namesakes.Store.Get<T>(string), a method made for type arguments with those arguments, CallShapes.Namesakes.Store.Get<int>(string) in a uses answer, and a conversion operator with its return type after it, CallShapes.Namesakes.Amount.op_Explicit(Amount) → long, since two of them can differ in nothing else. Parameter types and type arguments are written as C# writes them, by keyword or short name: a parameter passed by reference with its keyword, ref, out, in or ref readonly; a nullable value type as int? or T?, except before a member's name, System.Nullable<int>.GetValueOrDefault(); a two-dimensional array as int[,]; and an array of arrays with the outermost array's brackets first, int[][,] for an array of two-dimensional arrays. A line that would read the same as another line of its answer in this short form is written in full, every type with its namespace and the classes enclosing it, as find_methods writes the two explicit conversions of CallShapes.Namesakes.Voucher, whose return types share a short name:

static CallShapes.Namesakes.Voucher.op_Explicit(CallShapes.Namesakes.Voucher) → CallShapes.Namesakes.Alpha.Badge
static CallShapes.Namesakes.Voucher.op_Explicit(CallShapes.Namesakes.Voucher) → CallShapes.Namesakes.Beta.Badge

Only list_members and compare's member lists print declarations, which show what the reference form leaves out: this before an extension method's first parameter, params, a parameter's default, and the @ C# needs before a name that is a keyword, object @object.

Every tool takes these forms back, so a name from one answer can be passed to the next tool. type_name also accepts the reflection form (Outer+Inner, System.Func`2) and an argument list (System.Func<int, bool>, whose argument count is the arity). A name is looked up among the types the assembly defines, references and forwards to another assembly together. A name written without arity means the one type of that name without type parameters where there is one, and otherwise the only type of that name, so a name the assembly gives only to generic types of its own means the type without type parameters it references or forwards. A name several generic types share, such as System.Func, is an error that lists them. compare first reads a name as written in both builds, so a class only one build has is answered as that build's, and a name without brackets that finds a different class in each build is an error naming both: Type name 'BaseShift.Arity.Crate' matches BaseShift.Arity.Crate<> in A and BaseShift.Arity.Crate<,> in B. Name one as listed. An array type written as C# writes it, byte[] or Shop.Part[][,], is taken by analyze with kind extension_methods and by decompile, analyze and compare with member_name, to find the extension methods code can call on such an array; every other question refuses it.

Member lookup. decompile, analyze and compare find a member of type_name by member_name. A name without a hint means the member of the most derived class that declares it, whatever kind of member that is, so a field that hides a base class's method of its name is the field; the method stays reachable through a hint or by asking the base class. A constructor is .ctor or the type's own simple name, Vault for CallShapes.Vault, and is looked for on that type alone. A static constructor is .cctor only, and a struct that declares no constructor has none, so where one is created is a question for analyze's instantiated_by. An accessor is named by its IL name, get_Count, set_Count, add_Changed or remove_Changed. A member C# implements explicitly, which it names after the interface, System.IDisposable.Dispose, is reached by its plain name only where no other member has that name. A name C# writes with @ before a keyword, @base, means the keyword.

Brackets after a method's name give its type parameters: Get<T>, Get<int> and Get<> each mean the Get with one type parameter, and Take<U> beside Take<T> selects by the names. A name without brackets means the methods without type parameters wherever the name has both, so Get on CallShapes.Namesakes.Store is Get(string), not Get<T>(string). Overloads are told apart by a hint of up to three parameters, each of which needs member_name: parameter_count; parameter_types, the parameter types in order as type patterns; and return_type, which selects among conversion operators that differ in their return type alone. The hint is a filter, not a tie-breaker: a lone method that does not satisfy it is not returned, and that no overload matches is an answer of its own. It is matched against the type, then each base class, then the extension methods, then the explicit interface implementations, and the most derived level that satisfies it wins, so an overload a base class declares is found. It is held as an exact fit first, through that whole search, and only where nothing fits exactly is it held loosely, as find_methods holds a pattern, so an exact fit on a base class comes before a loose one on the class asked about. So Truncate with parameter_types decimal means Truncate(decimal) beside Truncate(ref decimal). A hint that no method without type parameters satisfies is held against the generic ones as well, so Put with parameter_types T on CallShapes.Namesakes.Store means Put<T>(T) beside Put(string). Where the name or the hint leaves several methods, or none, the error lists them and says what tells them apart, see Troubleshooting.

Where no member of the name answers, the name finds an extension method the inspected assembly declares for the type, one of its base classes or one of its interfaces: any static method marked as an extension method, as a C# static class, a Visual Basic module or an F# class declares one, with its receiver passed by value or by ref, in or ref readonly. One whose receiver is a type parameter is found through every type that meets its constraints, by C#'s rule as the decompiler checks it, which differs from C# in four cases: it takes unmanaged for struct, lets a ref struct meet a method without constraints, fails a constraint that names a second type parameter, and lets a generic type asked without type arguments meet a constraint only where every construction of it does. A property, field or event of the name comes before any number of extension methods, except for call_sites and compare, which look for a method. The answer names the method under the class that declares it and marks it with the type it extends, here asked through another library's class of the test assembly ExternalUser.dll:

// ExternalUser.Extended.KettleExtensions.Boil(Kettle) → void [extension method on ExternalLib.Extended.Kettle]

A method whose receiver is a type parameter is marked with the type parameter and its constraints, [extension method on T where T : ExternalLib.Extended.IVessel], and one for an array type with the array, [extension method on System.Byte[]]. Through an array type, a public instance member of System.Array or System.Object of the name comes first and is answered as through that class, while a static one such as System.Array.Reverse does not; then come the extension methods C# would bind on such an array, except those for Span<T> and ReadOnlySpan<T>, to which C# 14 converts an array, so a method for a span is not found through an array. Through a type another assembly defines, see Types from other assemblies.

Type patterns. parameter_types and return_type take patterns rather than exact names. A pattern is a type's name, its full name, the end of its full name after any ., or a C# keyword (int, string). It matches the declared type only, not a base or derived one. List matches any List<T>, List<> any one-argument List, and List<int> only that one. Brackets at the end are read as C# writes an array, the outermost array's first and a comma for each dimension past the first: int[,] matches a two-dimensional array and int[][,] an array of them. A trailing * matches a pointer, and a tuple matches as the ValueTuple<...> it prints as. A trailing ? is read as C# reads it: int? matches the nullable type alone, string? what string matches, and T? both the nullable form of a struct's type parameter and a type parameter. A ref, out or in prefix matches only a parameter passed by reference, whichever keyword it has. A type copied from a line that names a member as declared, as find_methods and the headers write it, matches what it came from, and so does a nullable type copied from the decompiled code, such as string? or T?. A uses line names a member as the code uses it, so its parameter list passes back only where it reads as the declaration's: Crate<T>.Fill(T, List<T>) does not find Crate<>.Fill(TItem, List<TItem>).

find_methods holds a pattern loosely: int also matches int?, [] an array of any number of dimensions, and a pattern without a prefix a parameter passed by value or by reference. An overload hint in decompile, analyze or compare is held exactly first, see Member lookup: a pattern without a prefix fits only a parameter passed by value, int does not fit int?, a name without type arguments fits only a type without them, [] fits only an array of one dimension, and T? fits a type parameter only where the code marks it T?.

Generated code. The tools that list types or members, find_types, find_methods, list_members, search_code, analyze and compare, take include_compiler_generated. Left false, they hide what the compiler or a source generator created: closures, lambdas, iterator and async state machines, anonymous types, backing fields and the other fields a compiler adds beside the member they belong to, the field an enum keeps its value in, <PrivateImplementationDetails>, and Unity and Burst source-generator output. A generated type named by type_name is listed or searched whatever the switch says, in list_members, find_methods and search_code, since it was asked for by name, and analyze lists generated results when the symbol it is asked about is generated itself: the member where member_name is given, and the type otherwise. Code the compiler moves out of the method it is written in, a lambda, a local function, an iterator or an async method, is reported under that method by analyze and search_code and compared as part of it by compare.

Accessibility. The tools that list API, find_types, find_methods and list_members, take accessibility: public, public_protected (the default, which also covers protected internal and private protected), or all, which adds internal and private. What it leaves out is counted in a Not shown: line, see Lists. The other tools are never filtered by accessibility, because an analysis, a comparison or a search of the code must see everything.

Types from other assemblies. A type the inspected assembly uses but another assembly defines is known to ILens by the assembly's references to it, and a type the assembly forwards to another assembly by that forward. A tool that needs the type's definition says where it lies, so you know which assembly to inspect instead: System.String is not defined in this assembly; it comes from netstandard, Version=2.0.0.0. for the test assembly CallShapes.dll, and System.String is not defined in this assembly, which forwards it to System.Private.CoreLib, Version=10.0.0.0. for the .NET runtime's System.Runtime.dll. analyze answers questions about such a type from the inspected assembly's own references to it, list_members with include_inherited reads the members of base classes another assembly defines, and decompile, analyze and compare find by name an extension method the inspected assembly declares for such a type, as through a type it defines.

Through another library's type, a member of the type with the name comes first where C# would bind it for a call from the inspected assembly, and keeps its answer, which for decompile is the error naming where the type comes from. That is a public instance member, an internal or protected internal one where the library grants the inspected assembly its internals, and for an interface a member of a base interface. A protected, private protected, private or static member, and an internal one the library does not grant, do not keep the extension method out. With an overload hint, every method the inspected assembly's code can name comes first where the hint fits it, static and protected ones included. Where the type's library is not found, the members the inspected assembly's references name on the type come first, an extension method is found only for the type itself or through a type parameter without constraints, and the answer says what was not read:

// Not checked: whether ExternalLib.Extended.Kettle or its base types have a member Boil, which C# would take first; ILens could not load ExternalLib, Version=1.0.0.0

An answer that leaves something out for want of another assembly's class says so in a clause of an error, a Not shown: line under list_members, or a Not checked: line under decompile, analyze and compare, and gives one of three reasons. ILens takes the first file of the library's name it finds, beside the inspected assembly, then at the top of each allow-root in the order given, then among the installed .NET libraries, so the remedy is always to make the right file the first one found:

  • ILens could not load ExternalLib, Version=1.0.0.0: no file of the library's name was found. Give the folder that holds it as an allow-root.
  • <library> as loaded from <file>, Version=<version found>, does not hold <class>; referenced is Version=<version referenced>, the last clause only where the versions differ: the file found is another build than the one the assembly was made against. Give the folder of the right build as an allow-root ahead of it. For a framework class, which ILens otherwise reads from the .NET installed on the machine, that is the folder of the framework the assembly runs on, such as a game's own libraries.
  • ILens could not load <library>, Version=<version>: the file found, <file>, holds the assembly <other>: the file is not the library its name says.

Reference assemblies. An assembly marked as a reference assembly holds a library's declarations without their code: a .NET reference pack, a .NET Framework reference assembly, a compiler's reference assembly, or a copy made for building against, such as a publicized assembly in a build folder. Its method bodies are placeholders, so a question that reads code is refused there rather than answered from them as "nothing uses it": analyze with used_by, instantiated_by, read_by, assigned_by, call_sites or uses, search_code, and find_harmony_dependencies. The error says where to ask instead, here for System.Collections.dll of the .NET 10 reference pack:

Error: ArgumentException: This assembly is a reference assembly, which holds a library's declarations without their code, so 'used_by' cannot be answered from it; ask the build the library runs as. exposed_by, extension_methods, applied_to, overridden_by, implemented_by and implements read declarations alone and answer here.

The build the library runs as is the one the runtime loads, such as the library of the same name in the installed .NET's shared folder for a .NET reference pack. The questions that read declarations alone answer as for any assembly, and compare compares no body of a reference assembly and says so beneath its lists.

Strict arguments. An argument name a tool does not declare is rejected with the list of valid names. A parameter that does not apply to the question asked is rejected too, such as parameter_name with a kind other than call_sites, or an overload hint without member_name in decompile, analyze or compare. A value a parameter does not take is an error that names the parameter and what it takes, with every wrong value of a call in one answer, as here for a find_types call:

Error: ArgumentException: Invalid value 7 for argument 'accessibility'. Valid values: public, public_protected, all. Invalid value 1.5 for argument 'limit'. Expected an integer.

A required parameter left out or null is Missing required argument 'kind'. An exact type_name or namespace that names nothing is an error too, not an empty answer; analyze, which answers about types the assembly only uses, ends its empty answer about such a name with a line saying that the assembly neither defines nor references a type of that name. A silently dropped filter, or a value read as another one, would return a plausible answer to a question nobody asked.

Discovery

find_methods read-only

Find methods across the assembly by name, parameter types or return type, or list one type's methods with type_name. Any combination of filters narrows the search.

Parameters

assembly required string
Path to the .NET assembly to inspect (must be under an allowed root).
name_contains optional string
Case-insensitive substring of the method's name, without namespace or declaring type. A constructor's name here is .ctor.
return_type optional string
Return-type pattern, matched by the rules of parameter_types.
parameter_types optional string[]
Parameter-type patterns, in order; the method takes exactly these. Each is matched loosely: int also matches int?, and a trailing [] an array of any number of dimensions, while int[,] matches a two-dimensional one. See type patterns.
parameter_count optional int
Number of parameters the method takes. If parameter_types is also given, the two must agree.
namespace optional string
Exact namespace of the declaring type, e.g. System.IO; its sub-namespaces are not included.
type_name optional string
Fully qualified declaring type, e.g. System.IO.File. An exact name asserts that the type exists, so a name that finds no type is an error rather than an empty list. A compiler-generated type named here has its methods listed whatever include_compiler_generated says.
type_name_contains optional string
Case-insensitive substring of the declaring type's name, without namespace; cannot be combined with type_name. Matching nothing is an ordinary empty result.
accessibility optional public | public_protected | all
Default public_protected, which also covers protected internal and private protected; all adds internal and private. It filters the methods by their own accessibility. See accessibility.
include_compiler_generated optional bool
Include what the compiler or a source generator created, such as names starting with <. Default false. See generated code.
limit optional int
Maximum number of methods to list. Default 100.

A whole body is one call away: decompile on either build for its C#, or a context larger than the method for both bodies in one diff, each change marked.

Two bodies the comparison finds equal get a verdict line alone, in either format, since a copy would show nothing that changed:

// BaseShift.Generated.Renumbered.LocalFunctionCapturing(int) → int — bodies are identical in both assemblies.

When the C# reads alike while the IL differs, the line ends — bodies decompile alike in both assemblies, but their IL differs; format il shows where. A method that has a body in neither build is no pair of equal bodies: the line ends — neither assembly has a body for it: abstract in A, extern in B., with each build's reason, abstract, extern or provided by the runtime, where its metadata gives one. A method only one build has is the whole difference, so its code follows a line that says which build has it: // BaseShift.Generated.Renumbered.Inserted(int) → long — only B has it.

A line then names both, each as decompile's comment does, with [inherited from X] or [extension method on X] where the type asked about does not declare it, and the verdict or the diff under it shows whether more than the signature changed:

Constants. A constant, an enum member included, is answered with its values in one line: // BaseShift.Values.Limits.Changed — 5 in A, 6 in B., // BaseShift.Values.Limits.Kept — 1 in both assemblies., // BaseShift.Values.Limits.Added = 7 — only B has it., and for two constants the member list counts as two members, with their types: // BaseShift.Values.Limits.Wide → int in A and BaseShift.Values.Limits.Wide → long in B are different constants — 5 in A, 5L in B. An inherited constant carries its mark, // BaseShift.Values.Derived.Limit [inherited from BaseShift.Values.Base] — 5 in A, 6 in B. The name means the constant where the nearest class that has the name declares one, as in C#; a hint asks for a method.

Fields, properties and events. A property or an event has no body of its own. One that only one build has comes with its code, as decompile shows it, or with format il with the IL of each accessor under a line that names it, such as // BaseShift.Sides.Panel.get_Title() → string:

public string Title { get; set; }

Where none does, the error points to assigned_by; may set it names a constructor that passes the field's address to code ILens cannot follow, such as a method of another assembly. Extension methods and moved types. Each build finds an extension method through the type asked about as decompile does. Where one build finds it and the other declares it as well but its lookup does not take it, the line says why in place of only A has it: — only A finds it through <type>; in B the type has a member of that name, which C# takes first., or for a method whose first parameter is a type parameter:

A build that does not define the type asked about but references it, as after the type moved to a library, is asked through the type it references, so a method one build declares on the type and an extension method the other declares for the library's type are compared as two different methods. A line that says only one build has a member then ends with where the other build takes the type from: — only A has it; in B <type> comes from <assembly>. Where a build's lookup could not read a class that might declare a member of the name, the answer starts with the Not checked: line that decompile writes under its comment.

Reference assemblies. A build marked as a reference assembly holds a library's declarations without their code (see reference assemblies), so no body of it is compared or shown. Troubleshooting

Every tool error reaches the caller as Error: <ExceptionType>: <message>. The messages below are shared by several tools; the ones particular to a tool are listed under that tool.

No allowed roots configured. The server cannot load any assemblies. Launch with one or more --allow-root <directory> flags.

The server was launched without --allow-root. Add one or more --allow-root <directory> arguments to the args array in .mcp.json and start a new session. list_allowed_roots reports the same condition without failing.

Path is not under any allowed root: ... Allowed roots: ...

The requested assembly lies outside every configured root, as the path is written. The message lists the roots that are configured; a root given through a symbolic link or junction is listed with (resolved: <path>), the folder the link pointed to when the server started, where that is another path. Either point the call at a file inside a root, through the root's link or by its real path, or add the containing directory as another --allow-root. A path written through a link that lies outside every root is refused here even where the link leads into a root.

Path resolves (via a symbolic link or junction) to a location outside any allowed root: ...

The path passed the check as written but resolves to a real target outside the roots. This is the link check doing its job: a link planted inside a root cannot be used to reach outside it. The message lists the roots as the one above does. The same message answers a request through a root's link that was moved to another folder while the server runs, since a root stays the folder its link pointed to at startup; restart the server to follow the link, or ask by the old folder's real path meanwhile. A chain of links that does not end, or cannot be followed, is rejected with Path has too many levels of symbolic links or junctions (possible cycle): ... or Path could not be resolved through its symbolic links or junctions: ....

Path contains '..' which is not allowed: ...

Parent-directory segments are rejected before normalization. Pass an absolute path with no .. components.

Assembly file does not exist: ... or Assembly path is empty.

The path is inside a root but names no file, or no path was given. Check the spelling and that the build actually produced the assembly.

MetadataFileNotSupportedException: PE file does not contain any managed metadata., BadImageFormatException: Unknown file format. or InvalidOperationException: Failed to load type system from ...

The file is not a .NET assembly: the first is a native DLL or executable, the second a file that is no Windows executable at all, and the third a file that holds .NET metadata but no assembly, such as a program database (.pdb). ILens reads compiled .NET assemblies only.

Assembly is N MB, which exceeds the M MB total memory budget on its own: ... Raise the budget with --max-total-size <MB>.

ILens holds an assembly's whole image in memory while it is open, so a file larger than the whole memory budget is refused before it is loaded. Raise the budget with --max-total-size <MB>.

Unknown argument '...' for tool '...'. Valid arguments: ...

An argument name the tool does not declare, often a parameter name from an older ILens release. Most filters are optional, so a silently dropped filter would return an unfiltered result that looks like an answer; the call is rejected instead. The message lists the valid names.

Invalid value ... for argument '...'. ... or Missing required argument '...'.

A value the parameter does not take, such as a kind that analyze does not have, a number or several comma-separated names for a parameter with listed values, or text that is no whole number for limit; or a required parameter left out or given as null. The message names each such parameter of the call and what it takes: Valid values: ... with the listed names, or Expected an integer., Expected a string., Expected true or false. or Expected a list of: .... A value with exactly one reading is taken without an error, see Tool reference.

This assembly is a reference assembly, which holds a library's declarations without their code, so ...

A question that reads code was asked of a reference assembly, whose method bodies are placeholders. Ask the build the library runs as; the message also names the questions that read declarations alone and answer on this assembly. See Reference assemblies.

Type not found: ...

No type the assembly defines, references or forwards has that name. The message ends with the types the name may have meant: Types of that name: ... where types of that full name exist with another count of type parameters, and otherwise the types of the name's last segment in any namespace or enclosing class, those that differ from the name only in the namespace where any does. Asked of the test assembly CallShapes.dll:

Error: ArgumentException: Type not found: Shop.Vault. Types named Vault: CallShapes.BaseCalls.Vault, CallShapes.Vault.

Types the assembly references or forwards are named in groups with their library, Types named Marker: this assembly defines ...; it references ExternalLib.Namesakes.Marker from ExternalLib, Version=1.0.0.0., and at most 40 types are named, the rest counted. analyze gives such a name an empty answer instead, whose last line says that the assembly neither defines nor references a type of that name and names the same types. find_types with name_contains finds the exact name.

... is not defined in this assembly; it comes from ... or ..., which forwards it to ...

The assembly uses the type, or forwards it, but another assembly defines it. Point the call at that assembly to read the type itself. analyze can still answer who in this assembly uses it, and decompile, analyze and compare still find an extension method this assembly declares for the type, see Types from other assemblies. A forwarded type is named with the assembly it is forwarded to, also where the assembly references it too; a reference that names no assembly reads ... is not defined in this assembly, which only references it. Where the assembly gives the name only to generic types of its own, the message names them, since you may have meant one, as in the test assembly ExternalUser.dll:

Error: ArgumentException: ExternalLib.Namesakes.Marker is not defined in this assembly; it comes from ExternalLib, Version=1.0.0.0. This assembly defines ExternalLib.Namesakes.Marker<>, ExternalLib.Namesakes.Marker<,>.

Type name '...' matches N types: ... Name one as listed.

A name written without arity matches several generic types and no type without type parameters, such as System.Func. Where the types are of more than one kind, defined, referenced or forwarded, they are listed in a group for each kind, as in ExternalUser.dll:

Error: ArgumentException: Type name 'ExternalLib.Namesakes.Crate' matches 2 types: this assembly defines ExternalLib.Namesakes.Crate<,>; it references ExternalLib.Namesakes.Crate<> from ExternalLib, Version=1.0.0.0. Name one as listed.

Types of one kind read matches 17 types this assembly forwards: System.Func<>, ... (the .NET runtime's System.Runtime.dll) or matches N types this assembly references but does not define: .... Pass one of the listed names, which carry their arity.

... is an array type, which only analyze with kind 'extension_methods' and decompile, analyze and compare with member_name take, to find the extension methods code can call on it.

An array type has no members of its own in an assembly. Ask about its element type, or ask one of the named questions for the extension methods that apply to such an array.

An array type writes its element with its type arguments, as C# does: ... names ..., which takes N.

The element of an array type was written without its type arguments, as in System.Collections.Generic.List[]. Write it as C# does, such as List<int>[].

Namespace not found: ...

No type of the assembly lies in that namespace or below it. Namespaces are matched exactly and case-sensitively.

Member '...' not found on ..., its base types, or as an extension method.

The name is not on the type, its base classes or among the extension methods that apply. list_members lists what the type has; an accessor is named with its prefix, get_Count, and a constructor .ctor or by the type's name. A lookup of a property or an event alone reads Property '...' not found on ... or its base types. and likewise for an event. Where a usual name does not apply, the message ends with what does: ; its indexer is named Chars: System.String.get_Chars(int) for get_Item, set_Item or Item on a type whose indexer has another name (asked of the .NET runtime's System.Private.CoreLib.dll); ; a struct that declares no constructor has none in the assembly, and instantiated_by lists where it is created, ; an enum has no constructor or ; its static constructor is named '.cctor' for .ctor or the type's name; and ; the methods named Run are CallShapes.Namesakes.Store.Run(), CallShapes.Namesakes.Store.Run<T>() for brackets whose count of type parameters fits no method of the name. When the search stopped at a base class ILens could not read, the message says the base types ILens could load and ends with the class and the reason, as in ExternalUser.dll without the folder of ExternalLib.dll among the allow-roots:

Error: ArgumentException: Member 'Level' not found on ExternalUser.Inherited.Probe, the base types ILens could load, or as an extension method; ExternalLib.Inherited.Sensor and its base types were not searched, since ILens could not load ExternalLib, Version=1.0.0.0.

The three reasons and their remedies are under Types from other assemblies; once the class can be read, the search goes on into it. Through an array type the message reads Member '...' not found on System.Byte[]: no public instance member of System.Array or System.Object and no extension method of this assembly that applies to it has that name., with ; what ... derives from was not read, since ... where the element's class could not be read.

... inherits ... from a base class this assembly does not define; ... comes from ...

The member is declared on a base class another assembly defines, so the inspected assembly holds no code for it. The message names the file that does: call decompile, analyze or compare on that file to read the member. A member the type's code cannot reach, a private one or an internal one its library does not grant this assembly, is passed over as C# passes over it, so an extension method of the name answers in its place; for such a member the error stands only where nothing else answers to the name.

'...' on ... has N matching overloads; ...: ...

The name, or the name with the hint given, fits several methods. The message lists them and says what tells them apart: specify parameter_count or parameter_types to disambiguate; they are same-arity overloads — specify parameter_types to disambiguate; write the type parameters of the one meant after its name, as listed; they differ in their return type alone, which return_type selects; these parameter types fit more than one; write those of the one meant as listed, as where a short type name fits classes of that name in two namespaces, and likewise this return type fits more than one; write that of the one meant as listed; or the candidates share their parameter types and cannot be narrowed further. Asked of CallShapes.dll:

Error: ArgumentException: 'op_Explicit' on CallShapes.Namesakes.Amount has 3 matching overloads; they differ in their return type alone, which return_type selects: CallShapes.Namesakes.Amount.op_Explicit(Amount) → int, CallShapes.Namesakes.Amount.op_Explicit(Amount) → long, CallShapes.Namesakes.Amount.op_Explicit(Amount) → decimal.

No overload of '...' on ... matches ...

A parameter_count, parameter_types or return_type hint was given and nothing satisfies it. The message lists every method of that name found across the inheritance chain, so the right hint is usually visible in the error itself, and a confirmed "no such overload" is often the answer that was being sought.

Property '...' on ... has N overloads — ...

The name is shared by several indexers, which C# names alike. Name the accessor of the one meant instead, get_Item or set_Item, with parameter_types; the message lists the candidates.

'...' on ... names N explicit interface implementations: ... Pass the full name of one instead.

The type implements several interface members of that name explicitly, such as two GetEnumerator methods. Pass the full name of the one meant, as listed, which includes its interface.

Property '...' on ... has no getter.

An accessor's name was asked for a property that lacks that accessor; the message reads has no setter likewise, and Event '...' on ... has no add accessor. or has no remove accessor. for an event.

Member '...' on ... is ambiguous — it exists as more than one member kind ...

One type declares the name as more than one kind of member, which only obfuscated or non-C# metadata produces. Names that classes at different levels of the inheritance chain use for different kinds do not trigger it: the member of the most derived class that declares the name answers. Pass an overload hint if the method is meant. An ordinary event does not trigger this either: the field the compiler keeps its subscribers in is recognized as part of the event.

parameter_count (N) contradicts parameter_types.Length (M).

Both overload hints were given and disagree on the number of parameters. Pass one of them, or make them agree.

parameter_count, parameter_types and return_type select a method overload, so they need member_name.

An overload hint was given to decompile, analyze or compare without a member to select. Add member_name, or leave the hint out to ask about the type.

Decompiled code shows numbers where names belong, or Unknown result type comments

A referenced assembly is not in an allowed folder. ILens finds an assembly's references beside it, at the top of each allow-root, and in the installed .NET; a reference it cannot find leaves the decompiler without its types, so enum values come out as numbers, such as (Glaze)1 for a value of another library's enum, and expressions of those types are marked as unknown. Add the folder that holds the missing assemblies, such as a game's own assemblies for a mod, as another --allow-root. The same missing library makes other answers end with a line that names it, see Types from other assemblies.

The tools do not appear at all

Almost always the two gates described under Integrating with Claude Code: an already-running Claude app holding a stale PATH, or a session that started before .mcp.json existed. Close Claude app entirely, relaunch it, and start a new session. The server also refuses to start when its own arguments are wrong. It then writes the reason to stderr as a line starting with [ILens] and exits, which the MCP client typically reports as a server that failed to connect:

  • [ILens] --allow-root path does not exist: ..., or is a file, not a directory, for a root that is no directory.
  • [ILens] Path could not be resolved through its symbolic links or junctions: ... for a root whose links cannot be followed, such as one below a folder the server may not list, and [ILens] Path has too many levels of symbolic links or junctions (possible cycle): ... for a chain of links that does not end.
  • [ILens] unknown argument: ..., followed by a usage line, for any other argument.
  • [ILens] --max-total-size must be a positive integer (MB): ... and [ILens] --max-search-seconds must be a non-negative integer (seconds): ..., and a line that names the value a flag is missing.

Appendix A: Alternative installers

For machines where winget is unavailable or locked down by policy, or when you would rather inspect the binary before granting it execution.

PowerShell one-liner

irm https://raw.githubusercontent.com/tadis174/ILens/main/install.ps1 | iex

Installs to %LOCALAPPDATA%\Programs\ILens\ and adds that directory to your user PATH. No admin elevation is needed.

Manual ZIP

Download ILens-windows-x64.zip from the Releases page and extract it anywhere. Then either add the directory to PATH yourself, or give the binary's full path in .mcp.json's command field.

Appendix B: Updating and uninstalling

winget. winget upgrade Tadis.ILens to update; winget uninstall Tadis.ILens to remove.

PowerShell one-liner. Re-run irm https://raw.githubusercontent.com/tadis174/ILens/main/install.ps1 | iex to update — the script overwrites the install directory in place and stops any running ILens processes first. Uninstall with irm https://raw.githubusercontent.com/tadis174/ILens/main/uninstall.ps1 | iex.

Manual ZIP. No automatic update mechanism — re-download ILens-windows-x64.zip and re-extract on each new release. To uninstall, delete the extracted folder and remove the PATH entry if you added one.

Appendix C: Installation troubleshooting

Antivirus or Windows Defender quarantines ILens.exe

Self-contained .NET binaries are sometimes false-positive-flagged on first sight. Check the quarantine and restore the file, or add an exception for the install directory — %LOCALAPPDATA%\Microsoft\WinGet\Packages\Tadis.ILens_*\ for winget, %LOCALAPPDATA%\Programs\ILens\ for the PowerShell script — before re-running the installer.

SmartScreen shows "Windows protected your PC"

This affects browser-downloaded ZIP installs, which carry Mark-of-the-Web. The winget and PowerShell paths do not. For a manual browser download, click "More info → Run anyway".

winget upgrade Tadis.ILens fails with remove: Access is denied: "...\ILens.exe"

A running ILens MCP server — a Claude Code session, Claude Desktop, or another AI client that registered ILens — holds an exclusive lock on the binary winget is trying to replace. Close every AI client with ILens registered and re-run the upgrade. The PowerShell install.ps1 path handles this automatically by stopping running ILens processes before extraction, so the same upgrade via irm ... | iex needs no manual cleanup. winget's portable installer type has no pre-install hook where an equivalent step could run.

Appendix D: claude mcp add CLI

A programmatic alternative for anyone who would rather not edit .mcp.json by hand:

claude mcp add ilens ilens -- --allow-root "C:\path\to\dlls"

The doubled ilens is intentional: the first is the MCP server alias — the same string that becomes the JSON key in .mcp.json — and the second is the binary on PATH after install. The -- separator before --allow-root is required so claude mcp add does not consume it as one of its own options.
